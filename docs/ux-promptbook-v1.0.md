## P00 | 통합 실행과 공통 제약
~~~text
너는 ‘박자표 피자 화덕’의 UX 구현자다. 첨부된 UX 리팩토링 설계서 v1.0이 최우선 제품 명세다. 요청한 저장소는 kimyounggaur/time_signature_pizza_oven_game, 비교 기준은 82bda2c81017b5022c85c686faff12545d6430d0이다. 파일을 못 읽으면 읽었다고 가정하지 마라. 현재 코드가 문서와 다를 때는 차이와 보존해야 할 실제 사용자 변경을 먼저 밝혀라.

목표: 신규 학습자가 별도 지도 선택이나 소리 확인 없이 첫 도마에서 같은 4분음표 조각을 두 번 눌러 2/4를 채운다. 이어 같은 조각 두 개를 남긴 채 한 개를 더 넣어 3/4를 만들고, 기준 음표는 그대로인데 한 마디에 한 박 더 들어감을 발견한다. 소리가 없어도 비교는 완결된다. 30초는 설계·관찰 목표이며 카운트다운이나 징벌이 아니다.

P01→P02→P03→P04→P05 순으로 수행한다. 각 단계의 통과를 증거로 확인하고 통과한 항목은 다시 만들지 않는다. 일상적인 구현 선택은 위임받았으므로 스스로 결정하고, 기능 회귀는 최소 수정으로 고친 뒤 재검사한다. 사용자 변경을 덮거나 기존 설계를 바꿔야 하거나 접근·검증에 필요한 조건이 없으면 그 단계에서 이유를 기록한다. Q18~19 선택 확장은 기본 작업에 끼워 넣지 않는다.

보호: 정규 5일·39주문·S1~S4·채점·해금·메뉴 69칸·엇박 선반·도장·룰북과 저장 v1을 보존한다. 맛보기는 진도, 성적, 수집 기록에 반영하지 않는다. 자유 화덕이나 가짜 정규 주문으로 구현하지 않는다. 엔진 TURN, 분수, 음표 길이·묶음 계산을 바꾸지 않는다. 배포 HTML은 npm run build로 재생성하며 직접 편집하지 않는다. 새 외부 런타임 리소스나 분석 도구를 추가하지 않는다. 이 프롬프트만으로 원격 푸시, main 병합, Vercel 배포, 사용자 모집은 하지 않는다.

단계별 보고서에 PASS/FAIL/NOT_RUN/BLOCKED, 실제 실행 명령·종료 상태, 비교의 기준이 된 증거를 적어라. 모의 오디오를 실제 청음으로, 브라우저 에뮬레이션을 실제 휴대폰으로, 예상 수치를 실측으로 쓰지 않는다.
~~~

## P01 | 기준판 고정: 단계 0
~~~text
공통 제약을 적용하고 실행 환경과 기준판만 확인한다. 아직 UX 소스를 수정하지 않는다.

1. git status --short, git rev-parse HEAD, git remote -v로 상태를 확인한다. 비교 기준과 현재 HEAD 차이를 읽는다. 사용자 변경이 있는 기존 작업 트리에서 빌드 생성물이 덮일 위험이 있다면 격리 사본에서 시험한다. reset, clean, 강제 checkout, 사용자의 작업을 숨기는 임의 stash는 하지 않는다.
2. README.md, docs/design-v1.0.md, docs/implementation.md, package.json, scripts/build.mjs, tests/를 읽는다. Node 20 이상에서 npm test → npm run build → cmp index.html dist/index.html을 실행하고 실제 수치와 종료 코드를 기록한다. 이어 npm run dev로 실제 브라우저 #test를 검증할 수 있는지 확인한다. 기존 보고의 101 Node·96 자가검사는 옛 수치이며 룰북 테스트가 추가된 기준판에서 그대로 합격 숫자로 못 박지 않는다.
3. 사용자의 저장은 건드리지 말고 격리 프로필에 신규, active가 0번이 아닌 진행 중, 완료·메뉴·선반·S1 흔적이 있는 저장을 준비한다. 타이틀→영업일 지도→0단→소리 확인→d0-01을 기록한다. 정상 재개는 현재 체크포인트 주문 복원이며 조립 중 배치까지 복원한다고 가정하지 않는다.
4. 가능하면 320×568 및 데스크톱에서 첫 주문, 영업일 지도, 룰북을 캡처한다. 정규 한 마디 프리롤·두 번 연주와 자리 주문 A/B 패턴을 기준으로 보존한다. 맛보기 없는 현재 상태를 별도 기록한다.

통과: 기준 SHA와 작업 보호 상태, 기존 실패와 환경 제한, 실제 실행한 검사·빌드 및 현재 학습 경로를 기록했다. 기준판에서 난 실패를 변경판의 새 실패나 성공으로 섞지 않는다.
~~~

## P02 | 정규 진도와 분리된 모델: 단계 1
~~~text
P01의 기준 보고서를 읽고 src/taster.js 순수 모델과 저장·진입 계약부터 구현한다. UI의 최종 통합은 P03에서 한다.

1. initialTaster, reduceTaster, tasterView, resolveLanding처럼 DOM·스토리지·오디오를 직접 읽지 않는 접점을 둔다. 기본 상태 two(0..2)에서 ADD/UNDO로 하나씩 이동한다. 2가 되기 전 Bake는 거부하고, 2에서 추가 연타는 무반응이다. Bake→playTwo→정상 완료 또는 [바로 비교]→three(2), STOP→two(2). three(0..3)에서 ADD/UNDO를 허용하고 3에서 compare로 간다. 2/4 배열과 3/4 배열은 참조를 공유하지 않는다. compare에서 [하나 빼기]는 three(2). 모달·숨김·이탈 중 취소된 END는 무시한다.
2. capacity, lengthIn, dur, N/M/F와 기존 각도를 사용한다. 용량 2/4=1/2, 3/4=3/4. 온음표 기준 한 바퀴 아래 4분음표 한 조각은 양쪽 모두 90°이며 두 박 180°·세 박 270°다. 판마다 용량을 한 바퀴로 정규화하지 않는다. 엔진 cells는 8분음표 수다. ‘남은 박’ 표현은 4분음표 단위로 계산한다.
3. 진입 우선순위: 초기 #test 및 #d0~#d4 → 기존 유효 active와 타이틀의 [이어서 영업] → tasterSeenV1 또는 실제 학습 흔적이 있는 기존 타이틀 → 완전 신규의 빈 두 박 도마. 기본 설정만 저장되어 있거나 저장 키만 존재하는 것은 학습 흔적이 아니다. 재방문 판정은 원본 §3을 따른다.
4. 저장 키/버전은 pzo_save_v1 그대로. src/storage.js의 freshSave 기본값과 normalizeSave boolean 허용 목록에 settings.tasterSeenV1을 추가한다. 명시 종료/건너뜀/비교 완료에서 한 번만 쓰고, 조립·재생 중에는 기존 active, days, stats, menu, shelf, scenes를 바꾸지 않는다. 저장 실패 폴백·손상 백업·팁 초기화 동작 유지. 맛보기 완료가 soundChecked=true를 뜻하지 않는다.
5. 단위 테스트를 추가한다. 초과, 되돌리기, 같은 조각 2개 유지, 순수 상태, 해시·active 우선, 완료 토큰 정규화와 저장 실패 주요 경우를 독립 검증한다.

통과: Q01~Q04·Q07의 순수 모델 계약을 검증한다. 이 단계에서 실제 DOM·음향·활성 저장 연동까지 성공했다고 쓰지 않는다. 렌더·실제 진입은 P03에서 같은 Q-ID를 재검증한다.
~~~

## P03 | 무음으로 완결되는 첫 화면: 단계 2
~~~text
P02의 상태·라우팅 테스트와 설계서 §2~5·§7을 읽고 신규 맛보기의 화면을 붙인다. 실제 한 마디 오디오 합성은 P04에서 추가한다.

1. src/main.js의 초기 해시, render, titleRender, go/start, #screen 위임 이벤트에 taster 분기를 추가한다. src/shell.html과 src/style.css에 독립 마크업의 실제 button을 둔다. shellScreen의 key 갱신만으로 값 렌더를 생략하거나 매 탭 innerHTML 교체로 포커스를 잃지 않게 한다. 값 갱신과 모달 닫기 복귀를 분리한다.
2. 첫 화면은 ‘한 칸에 한 박. 빈자리를 채워요’, 두 자리와 큰 [조각 올리기] 하나, 보조 [하나 빼기]/[건너뛰기]. 두 번 눌러 ‘1박 남았어요’→‘2박, 꽉 찼어요’. 정확히 채우면 굽기 또는 비교 행동 활성. 3/4는 앞의 같은 두 조각을 유지하고 ‘같은 조각을 한 번 더’와 새 자리 ③을 보여 준다. 비교에서 ‘아래 4는 4분음표 기준, 위 숫자는 한 마디의 그 단위 수’를 읽을 수 있게 한다. P03 단독 결과에서는 음향이 구현된 척하지 말고 시각 시간축/정적 비교 경로를 표시한다.
3. boardSVG 등 재사용 시 기존 눈금과 큰 박 번호를 구별한다. 320×568, 360×640, 390×844, 데스크톱에서 판·문구·CTA를 점검한다. 주 버튼 48 CSS px 높이, 보조 버튼 44×44 이상을 목표로 두고 큰 글씨/200% 및 낮은 가로 화면은 스크롤 허용. 기존 551px 이하 회전 안내는 맛보기만 예외. Tab/Enter/Space, Backspace, 모달 복귀 초점, 실제 비활성 상태, 색·동작 없이 구별 가능한 번호/문자를 확인한다. 기존 정규 숫자 1~6·0 전체화면은 보존한다.
4. 다시 들어온 사용자에게 기본 [이어서 영업]을 유지하고 수동 맛보기는 보조 메뉴에 둔다. 맛보기 종료 때 active가 있으면 기존 checkpoint를 resume한다. 없는 경우 [첫 주문으로]만 start(d0,{fromTaster:true})를 호출한다. 이 연결에서만 자동 soundCheck를 생략하고 ‘들려요’나 현재 음소거로 기록하지 않는다. 지도와 설정의 기존 소리 확인은 유지한다.
5. d0-01 안내는 ‘방금은 한 마디, 이번에는 2분음표 한 개의 길이만큼’이라는 차이를 분명히 한다. 4분음표 하나→같은 조각 하나 더→굽기 순으로 안내한다. 정규 d0-01을 2/4 주문이라고 바꾸지 않고 다른 주문 도움이나 판정을 손대지 않는다. 맛보기에서 Game.startFree, serve, nextItem, checkpoint를 빌리지 않는다.

통과: 앞 단계 Q01~Q04·Q07을 실제 화면에서도 확인하고 Q05~Q09를 통과한다. 맨 처음 메뉴·소리 모달 없이 동작, 보호 저장·메뉴 카운트 deepEqual, 실제 첫 주문 진입 후에만 정상 기록이 생김을 확인한다.
~~~

## P04 | 한 마디 재생과 취소: 단계 3
~~~text
P03의 무음 경로를 보존하고 설계서 §6의 맛보기 전용 오디오만 붙인다.

1. src/audio.js의 정규 createAudioPlan, AudioEngine.play/_frame/stop/_interrupt와 main.js의 unlock, playRequest, 시각 콜백을 읽는다. 기존 정규 한 마디 준비+두 번 연주와 자리 주문 A/B, 0.2초 여유는 그대로 둔다. 새 계획 createTasterPlan은 한 마디 한 번, 전주 없음. eighth e=.30 기본/.45 느리게에서 2/4 시작 [0,.60], 종료 1.20초, 3/4 시작 [0,.60,1.20], 종료 1.80초. 느리게는 1.5배. 끝점에 추가 음이 나지 않는다. 첫 박 강조와 나머지 박을 나누되 조각 인덱스와 박 인덱스는 분리한다.
2. 실제 [구워 듣기]나 재생 버튼을 눌렀을 때만 오디오 활성화를 요청한다. 공유 시계·예약을 재사용하되, 준비된 소리만 시작부터 시각과 동기화한다. 볼륨 0, 음소거, 미지원·실패·지연이면 시각 시간축을 진행하고 늦게 켜진 오디오가 중간부터 끼어들지 않게 한다. [바로 비교]로 듣기를 건너뛰어도 목표를 이해할 수 있어야 한다. 모션 줄이기에는 번호의 정적 강조를 사용한다.
3. 재생 하나당 소유자/요청번호/현재 screen을 캡처하고, 다음 재생·지도·모달·숨김·멈추기·바로 비교에서 먼저 토큰을 무효화한다. 대기 중 unlock도 취소 범위에 포함한다. 예약 노드와 RAF/타이머를 정리하고 예전 END는 무시한다. 멈추기를 완료로 세지 않는다. 정규 오디오 중단과 맛보기 중단을 구별하고 맛보기에서 game.completeBake/stopBake를 호출하지 않는다. 판·룰북에 겹치는 전역 .on 토글은 피하고 현재 그림만 갱신한다.
4. 모의 시계로 Q10~Q13을 실행하고 정규 프리롤·반복·소리 전용 주문도 재확인한다. 첫 클릭, 대기 취소, 연타, 무음, 움직임 줄이기, 브라우저 숨김을 별도 로그로 구분한다.

통과: 한 마디 길이·박 강조, 예약·취소, 시각 대체 검사가 통과한다. 실제 휴대폰에서 들었는지는 장치별로 별도 기록한다.
~~~

## P05 | 통합·회귀와 수업 확인: 단계 4
~~~text
P01~P04의 결과를 모으고 Q01~Q17을 전체 재검증하라. 기준판과 같은 환경에서 npm test → npm run build → cmp index.html dist/index.html → npm run dev / #test를 실행한다. 신규 모듈은 scripts/build.mjs의 names에 의존 모듈 뒤, 자신을 읽는 selftest/main 앞에 등록한다. 두 번 빌드의 동일 산출물, 400KB 예산, 오프라인 외부 런타임 요청 0과 콘솔 치명 오류 0을 확인한다.

Q14: 정규 채점·정규 재생·자리·소리 필수 주문·오답/보조·다시 내기를 검증한다.
Q15: 기존 5일·39주문·4장면, 통과·도장·최고점, 메뉴 69와 선반 별개 집계, 자유 화덕·정규 S3 해금을 검증한다.
Q16: 맛보기 및 기존 화면에서 룰북 목차·삽화·닫기와 포커스, 중복 SVG ID/강조 충돌을 검증한다.
Q17: 루트/배포 HTML 동일, 오프라인 첫 접속과 #test, 기존 테스트 손실 없음. 예전 테스트 수치를 고정 답으로 쓰지 않는다.

U01: 실제 처음 보는 학습자 5명을 관찰할 수 있을 때에만 검증한다. ‘이 피자를 한 마디만큼 채워 보세요’ 이상으로 버튼이나 횟수를 알려주지 않는다. 첫 조작 가능 프레임부터 두 박이 찬 프레임까지 30초를 잰다. 그 후 ‘두 피자에서 같은 것과 달라진 것을 보여 줄래요?’라고 묻는다. 동일한 5명 중 4명 이상이 ① 도움 없이 30초 이내에 2/4를 채우고 ② 비교 후 4분음표 기준은 같고 3/4에 한 박 추가됐다고 설명해야 통과한다. 비교 설명까지 30초를 재지 않고, 개인정보를 남기지 않는다. 좁은 실기기와 무음을 포함한다.

보고: 자동과 브라우저 에뮬레이션, 실제 iPhone/Android, 실제 학습자 결과를 분리한다. 사람이 없으면 U01 NOT_RUN으로 두고 빈 관찰표를 만든다. 게이트 미통과/미확인에는 운영 반영을 보류한다. 되돌림이 필요하면 플래그로 신규 자동 진입/다시 보기만 끄는 방안을 쓰고 저장은 지우지 않는다. 이번 프롬프트만으로 배포하지 않는다.
~~~

## P06 | 선택 확장 A·B: 단계 5
~~~text
사용자가 선택 확장 구현을 요청했고 핵심 단계가 준비됐을 때만 실행한다. 첫 30초나 정규 S3 해금의 필수 조건으로 넣지 않는다.

A / Q18: 2/4에 4분음표 두 개와 2분음표 하나를 번갈아 둔다. 같은 템포·총길이(기본 1.20초), 박 표시 두 번, 음 시작만 두 번/한 번이다. 2분음표는 둘째 박에서도 이어지며 새 음이 나지 않는다. ‘긴 소리가 이어지는 동안 박은 몇 번 지나갔나요?’를 선택 질문으로 둔다.
B / Q19: 기존 DAYS의 S3 상태를 읽어서 3/4와 6/8을 비교한다. 같은 여섯 8분음표·길이·기본 속도에서 3/4는 2+2+2(큰 박 1·3·5번째), 6/8은 3+3(큰 박 1·4번째). 6/8을 3/4로 약분하지 않고 원래 발음과 묶음만 대비한다. 진입은 읽기 전용이며 정규 nextItem, 획득, 해금, 도장, 메뉴에 영향을 주지 않는다.

두 확장을 따로 테스트하고 준비된 항목만 노출한다. 실패한 기능의 버튼을 숨길 수 있으나 정규 S3와 핵심 맛보기는 그대로 둔다.
~~~

## 중단·재개 프롬프트
~~~text
첨부한 설계서와 프롬프트북, 마지막 단계 보고서를 대조한다. git 상태와 실제 테스트 증거를 확인하고 마지막으로 증명된 단계 다음의 첫 미완료 작업부터 진행한다. 저장이나 작업 트리를 초기화하지 않는다. 실패는 기존 기준 결함, 이번 회귀, 환경 미지원, 저장 호환으로 구분한다. 최소 재현→원인 경계 확인→해당 수정→관련 회귀 순서로 재실행한다. 기대 결과를 완화하지 않는다. 실제 기기나 학습자가 필요한 검증은 조건을 써 두고 미실행으로 남긴다. 보고서로 이후 세션이 이어서 작업할 수 있게 한다.
~~~
